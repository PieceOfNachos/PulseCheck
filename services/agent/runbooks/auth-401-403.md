# Authentication and authorization failures (401 / 403)

The endpoint is up and answering, but rejects the monitor's request as unauthenticated
or forbidden. Usually a credentials or access-policy change, not an outage.

## Symptoms

- `Expected 200, got 401` — Unauthorized: missing, invalid or expired credentials.
- `Expected 200, got 403` — Forbidden: credentials accepted but access denied.
- `WWW-Authenticate` header in the response; JSON body like `{"error":"invalid_token"}`.
- Fast responses with a small body; the health of the service itself looks fine.

## Likely causes

- API key or bearer token used by the monitor was rotated, revoked or expired.
- Endpoint that used to be public now sits behind auth (new middleware, gateway policy).
- WAF / bot protection or rate limiter blocking the monitor's IP or user agent (403).
- IP allowlist changed and no longer includes the monitoring egress addresses.
- Clock skew making signed requests or JWTs look expired / not yet valid.

## Diagnose

```bash
# Raw response and auth challenge
curl -si https://api.example.com/health | head -20

# Same request with a known-good token
curl -si -H "Authorization: Bearer $TOKEN" https://api.example.com/health | head -5

# Decode a JWT payload to check exp / aud / iss
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null; echo

# Gateway / WAF decision logs
kubectl logs -n api deploy/api-gateway --since=30m | grep -E " 40[13] "
```

- 401 without a token, 200 with one → endpoint now requires auth; update the monitor.
- 403 only from the monitoring IPs → WAF or allowlist rule.

## Remediate

- Point the monitor at an unauthenticated health route (`/health`, `/healthz`) where possible.
- Issue a new, scoped, read-only token for monitoring and store it in the secret manager.
- Add the monitoring egress IPs to the allowlist or exempt them from the WAF rule.
- Fix NTP / clock skew on the hosts validating tokens.

## When to pause the monitor / escalate

- Pause the monitor if the endpoint was intentionally moved behind auth and the
  monitor needs reconfiguring; there is nothing broken for real users.
- Escalate to the security / API gateway owners if real users are also getting 401/403
  after a policy change, or if credentials may have been revoked due to a leak.
